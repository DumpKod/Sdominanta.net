# Заготовка: одноразовые приглашения хранителей с QR

Следующий шаг, **не реализован**. Записано, чтобы следующая сессия начала с готового плана; перед работой — слово хранителя.

## Задача

Действующий хранитель приглашает нового. Новый хранитель получает свой ключ и TOTP-секрет один раз,
в виде QR, и больше их никто не видит: ни модель, ни сервер (на сервере — только отпечатки).

## Набросок

1. `/keeper/invite?otp=…` — только с cookie хранителя и кодом TOTP. Создаёт строку `invites`
   (`code` — `I-` + 8 + контрольный, `by` — знак пригласившего, `sign` — знак нового хранителя, `exp` — 24 ч, `used`).
   Ответ — одноразовая ссылка `/k/{I}`; сам код не хранится, только его SHA-256.
2. `/k/{I}` открывается один раз (атомарный `UPDATE … SET used = 1 WHERE used = 0 AND exp > now RETURNING`):
   страница с QR `otpauth://totp/…` и ключом хранителя, `Cache-Control: no-store`, `Referrer-Policy: no-referrer`.
   Повторное открытие — «приглашение уже использовано».
3. Ключ и TOTP-секрет генерирует Worker (WebCrypto) в момент открытия и сразу отдаёт; в базу пишутся только
   `key_sha256` и TOTP-секрет, зашифрованный `TOKEN_KEY` (AES-GCM).
4. Хранители перестают жить только в `KEEPERS`: `keepers(env)` читает секрет `KEEPERS` и таблицу `keepers`.
   Отзыв — строка `revoked_at`.

## Открытые вопросы для хранителя

- Хранить TOTP-секрет новых хранителей в D1 (зашифрованным) или по-прежнему только в секрете `KEEPERS`
  (тогда приглашение выдаёт значения, а хранитель сам вносит их в панель)?
- QR рисовать в Worker'е (SVG без зависимостей) или показывать строку `otpauth://` для ввода вручную?
- Нужно ли второе подтверждение от другого хранителя?
